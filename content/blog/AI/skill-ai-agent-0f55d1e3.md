Skill 越写越厚，Agent 还是反复犯同一个错。

这可能是很多团队现在最真实的尴尬。

业务越深入，踩坑越多；踩坑越多，团队就越想把经验沉淀成 Skill。检索有检索 Skill，客服有客服 Skill，数据分析有数据分析 Skill，内部工单还有一套更复杂的异常处理 Skill。

听起来很对。

但过一阵你会发现，系统开始变重了。

规则越来越多，触发越来越玄，上下文越来越吵。一个 Skill 说“冲突时先验证”，另一个 Skill 说“效率优先，快速给结论”；一个 Skill 要严格追问，另一个 Skill 又要求减少打扰。最后 Agent 不是更聪明，而是像背着一堆互相打架的便签在干活。

这就是今天很多 Agent 产品还没看清的矛盾：

**业务越沉淀，Skill 越多；Skill 越多，系统反而可能越臃肿。**

所以真正的问题，不是“再写一个 Skill”。

而是：**失败经验有没有进入反馈训练，变成模型下一次更稳定的行为偏好。**

> [!IMPORTANT]
> Skill 的价值，是把经验写进系统；训练的价值，是把经验写进模型行为。两者差一个层级。

## Skill 有用，但它不是学习

先把话说准：Skill 当然有用。

Prompt 像临时交代：“这次任务怎么做、输出什么格式、注意哪些坑。”Skill 更进一步。它把一类任务的流程、工具用法、异常处理、失败案例，沉淀成可复用能力包。

资料检索 Agent 不必每次从零想怎么查；数据分析 Agent 不必每次临场判断缺失值怎么处理；内部工单 Agent 也可以按既定路径处理权限、升级和合规话术。

这一步很关键。

它把“个人经验”变成“团队资产”。

但问题也在这里：**写进 Skill，不等于 Agent 学会了。**

Skill 本质上仍然是外部规则。它告诉模型“你应该这么做”，却不意味着模型在压力、噪声、工具失败、信息冲突时，真的更偏好正确路径。

新人读过 SOP，不等于经历过复盘。

Agent 读过 Skill，也不等于形成了肌肉记忆。

**Skill 是把失败写进文档。训练是把失败写进行为。**

![Skill 能沉淀经验，训练才能把失败变成行为](https://assets.zhangjian94cn.top/images/blog/skill-ai-agent-0f55d1e3/finetune-2026-v7-fig1.png)

更麻烦的是，Skill 会膨胀。

一开始它是经验库，后来可能变成规则沼泽。上下文被塞满，优先级不清楚，旧规则没人删，新规则不断加。团队以为自己在增强 Agent，实际可能是在增加 Agent 的决策噪声。

这就是 Skill 的天花板：它能管理经验，但不能天然完成学习。

## Agent 要训的不是答案，是过程

这也是为什么微调又被重新讨论。

但这次不是老式“喂答案”。

SFT（Supervised Fine-Tuning，监督微调）像刷题：给模型一批“输入 - 标准输出”，让它模仿。客服话术、文本分类、信息抽取、固定格式输出，SFT 很有效。

可 Agent 不是只回答一道题。

它要理解需求、选择工具、查询系统、判断信息够不够、处理冲突、应对 API 超时，最后再形成结论。

真正决定成败的，往往不是最后一句话，而是中间那串动作。

这时 RFT（Reinforcement Fine-Tuning，强化学习式微调）的价值就出来了。

**SFT 教模型：应该说什么。**

**Skill 告诉模型：应该参考什么流程。**

**RFT 训练模型：什么行为更值得被强化。**

这三者不是替代关系，而是层级不同。

Prompt 解决一次任务的指令问题。

Skill 解决一类任务的经验复用问题。

RFT 解决失败之后的行为改变问题。

这才是关键。

因为 Agent 的壁垒，不是它读过多少规则，而是它能不能在失败后真的换一种更好的做法。

![Skill 是外部规则，RFT 是行为偏好训练](https://assets.zhangjian94cn.top/images/blog/skill-ai-agent-0f55d1e3/finetune-2026-v7-fig2.png)

## 难点不是多跑几次，而是谁来判好坏

训练 Agent 最难的，不是让它多生成几条结果。

真正难的是：**什么叫做对？**

代码 Agent 可以看测试。客服 Agent 要看用户满意度和合规。搜索 Agent 要判断来源可信度。企业流程 Agent 还要处理权限、异常、业务规则和责任边界。

奖励很贵。

所以 GRPO、RULER、ART 这些方法值得关注。它们解决的不是“再写规则”，而是“如何把轨迹变成训练信号”。

GRPO（Group Relative Policy Optimization，组相对策略优化）的直觉很锋利：

**别急着给每个答案打精确分，先比较哪条轨迹更好。**

同一个任务，Agent 跑出 4 条路径：

A 查错资料。
B 查对资料，但结论含糊。
C 查对资料，也给出清楚判断。
D 没查资料，直接编。

你不必纠结 C 是 8.7 分还是 9.2 分。你只要知道：**C 比其他几条更好。**

RULER（Relative Universal LLM-Elicited Rewards）可以理解为让 LLM 裁判比较多条轨迹，而不是孤立给单个答案打分。

ART（Agent Reinforcement Trainer）则把流程工程化：记录 trajectory，也就是完整任务轨迹；交给评估系统比较；再用 GRPO 或类似方法更新模型或策略。

翻译成产品语言：

过去你有一个会读 Skill 的 Agent。

现在你开始有一个会被复盘、被比较、被训练的 Agent。

**失败不再只是 bug，而是训练材料。**

![多条失败轨迹和裁判反馈变成训练信号](https://assets.zhangjian94cn.top/images/blog/skill-ai-agent-0f55d1e3/finetune-2026-v7-fig3.png)

## 趋势已经转向反馈系统

最近 GLM-5.2 相关的 slime，也在强化这个信号。

它不是普通应用层工具，而是面向 RL scaling 的 LLM post-training framework，连接 Megatron 和 SGLang，支持自定义数据生成、奖励、环境交互。官方 README 还明确说，slime 是 GLM-5.2、GLM-5.1、GLM-5、GLM-4.7、GLM-4.6、GLM-4.5 背后的 RL framework。

这件事不用展开成项目介绍。

重点只有一个：

**行业正在把后训练、轨迹、奖励、环境交互，放到越来越核心的位置。**

Agent 的竞争，正在从“谁会写提示词”，走向“谁能组织反馈系统”。

这对产品经理、开发者、创业者尤其重要。

因为 Skill 仓库并不难复制。你有检索 Skill，我也能写；你有客服 Skill，我也能整理；你有工具调用流程，我也能搭。

真正难复制的，是你在真实业务里积累的失败轨迹。

哪些问题最容易误判？哪些工具结果最容易被错读？哪些场景必须追问？哪些回答看似完整，其实没有完成任务？哪些路径虽然慢一点，但更可靠？

这些东西，才是垂直 Agent 的金矿。

![AI Agent 的反馈训练壁垒](https://assets.zhangjian94cn.top/images/blog/skill-ai-agent-0f55d1e3/finetune-2026-v7-fig4.png)

## 别把 Skill 仓库当护城河

未来成熟的 AI 团队，维护的不会只是 Prompt 仓库、Skill 仓库和工具配置。

还会有失败轨迹库、评价规则库、任务样本库、人工校准集、工具调用日志。

听起来重，但这才像真正的工程。

当然，LLM 裁判不是银弹。如果裁判偏爱长答案，模型就会学会啰嗦；如果裁判忽略事实错误，模型就会越训越自信；如果模型学会迎合裁判，而不是真正完成任务，这就是 reward hacking。

> [!WARNING]
> LLM 裁判降低的是奖励设计门槛，不是取消人的判断责任。反馈系统不校准，训练只会把错误偏好放大。

所以现实路径不是一上来全自动。

先选一个窄任务。记录完整轨迹。人工校准评价标准。再把高质量失败样本回流为训练信号。

最后判断一个 Agent 项目有没有长期壁垒，我只看三个问题：

- 有没有记录完整失败轨迹？
- 有没有稳定定义什么算成功？
- 有没有把反馈回流到模型行为里？

Prompt 不会消失。

Skill 也不会消失。

但它们都不是终点。

**Prompt 是临时说明。**

**Skill 是经验沉淀。**

**失败样本是资产。**

**反馈训练，才是 Agent 从“会读规则”走向“真的会做事”的分水岭。**

如果一个 Agent 不能把失败变成行为偏好，它就只是在一次次重新开始。
